# 案件の見つけ方

`job-screening.md` は「見つけた案件をどう判定するか」、`proposal-templates.md` は「どう提案するか」を定義している。本ファイルは**その手前 — どこでどう見つけるか**を定義する。提案ファネルの入口。

---

## 中核原則: 量ではなく速度

**提案の価値は時間とともに減衰する。**

- 1案件に**50件以上の応募が集まる**ことがある
- 募集開始から日数が経つと、発注者側で既に候補が固まっている
- 募集直後の提案は、発注者がまだ本気で読んでいる段階に届く

したがって **「週末にまとめて5件提案する」より「毎日新着に1件ずつ反応する」方が、同じ提案数でも受注率が高い**。巡回は毎日、提案はその場で送る。

---

## 役割分担

| 工程 | 担当 | ユーザーの所要時間 |
|---|---|---|
| 通知の確認・保存検索の巡回 | **ユーザー** | 5分（複数件まとめて） |
| 募集要項を Claude に渡す | ユーザー | 1分/件 |
| Tier判定・見積もり・提案文の作成 | **Claude** | — |
| 内容の確認と送信 | **ユーザー**（最終責任） | 3分/件 |

**ユーザーの実時間は約5〜7分/件。週5件で週30分前後。**

### 巡回そのものは自動化しない

ブラウザ自動化を使えば技術的には巡回できるが、採らない。

- **公式APIが存在しない。** ランサーズの「オープンプラットフォーム」はパートナー企業向けのB2B連携であり、個人の案件収集用ではない。サンクションされた自動取得経路がない
- **利用規約の禁止事項を未確認のまま自動アクセスするのは、再取得不能な評価アカウントを担保に取る判断になる。** 検討するなら、まず各社の利用規約の禁止事項を原文で確認するのが順序
- **ログイン自動化はbot検知の対象になりやすく、検知時の結果がアカウント制限**であるため損失が非対称
- `job-screening.md` で「対象サイトの規約と robots.txt を必ず確認する」と定めている以上、自分が未確認のまま踏み込むのは一貫性を欠く

**そして実務的に、そこまでする必要がない。** 下記のとおりプラットフォーム自身が正規のプッシュ経路を提供しており、自動化で得られる利得は小さい。

⚠️ **Claude の出力をそのまま送信しない。** 確認せずに送ると、`delivery-workflow.md` Phase 4 の「検証は人間が責任を負う」という原則が営業工程で崩れる。提案内容の責任はユーザーが負う。

## 探索の3経路

| 経路 | 位置づけ | 内容 |
|---|---|---|
| **新着通知** | **最優先で設定** | 正規のプッシュ経路。これが巡回負荷を最も下げる |
| **保存した検索条件の巡回** | 主軸 | 毎日、新着順で確認 |
| 待ち受け | Phase 2以降 | ココナラ出品、ランサーズの直接依頼（スカウト） |

⚠️ **スカウトは主軸にできない。** プロフィールと無関係な分野のスカウトが届くという報告があり、質のばらつきが大きい。補助経路として扱う。

## プラットフォーム別の設定手順

**通知の設定が最優先。** ここを済ませれば「毎日サイトを見に行く」負荷の大半が消える。

### ランサーズ（手数料が最も低い。単価帯1〜10万円では優先）
- [ ] マイページの**通知メール設定**から、新着仕事通知メールが欲しいカテゴリにチェックを入れる
- [ ] 下記キーワードで検索し、**検索条件を保存**する（「保存した検索条件」からアクセスできる）
- [ ] 検索時は「仕事条件で絞る」の**「募集中の仕事のみ」**にチェック（募集終了案件を除外）
- [ ] 気になるが即断できない案件は**ウォッチリスト**に入れる（終了1〜2日前に通知が来る）

#### ✅ 実測で確認済みの経路（ランサーズ／2026-09-02時点）
- 送信元は **`noreply@lancers.co.jp`**（`lancers.jp` ではない）。メールで絞り込む際はドメインに注意
- カテゴリ別の新着通知が**毎日**届き、1通に案件が数件、**依頼金額・方式・募集締切つき**で載る。クラウドワークスより情報量が多く、Tier判定の一次スクリーニングに使える
- ただし掲載されるのは概要のみ。**判定には募集要項の全文が必要**

⚠️ **通知カテゴリの偏りが最大の問題（2026-09-02実測）**

| 通知カテゴリ | 1日あたり件数 | Tier |
|---|---|---|
| YouTube動画編集・加工 | 4〜5 | C |
| ショート動画編集 | 4 | C |
| 記事作成・ブログ記事・体験談 | 5 | C |
| AIライティング | 2 | C寄り |
| データ収集・入力・リスト作成 | 5 | C（**タスク形式が中心**。実測: 5円/件・11円/件、予算上限5,000円） |
| ChatGPT開発 | 1 | 要判定 |
| AI自動化・エージェント開発 | 1 | 要判定 |

**通知の約9割が Tier C。開発系は1日1〜2件しか流れてこない。**
これは登録スキル／通知カテゴリが動画編集・ライティング・データ入力に向いているためで、決めた立ち位置（業務自動化軸＋開発対応）と食い違っている。

→ **対処**: https://www.lancers.jp/mypage/receive_email から「AI・システム開発・運用」系を残し、動画・ライティング・**タスク系**を外す。あわせて登録スキルも立ち位置に合わせる。**これを直さないと週5件のTier A確保は成立しない。**

⚠️ **「データ収集・入力」カテゴリを切る理由を取り違えないこと。**
データ処理そのものは Claude と最も相性が良く、`job-screening.md` の完結度スコアでは満点になり得る。切る理由は**内容ではなく報酬構造**にある。

ランサーズのこのカテゴリは `work/search/task/collect` — **タスク・作業配下**であり、実測した10件は 5円/件・11円/件のタスク形式か、予算上限5,000円のプロジェクトだった。タスク形式はプラットフォームの画面で1件ずつ入力する必要があり、そもそも自動化できない。

**固定報酬 × ファイル納品のデータ整形案件は Tier A の最有力**なので、それはシステム開発系カテゴリで拾う。判定は `job-screening.md` STEP 2.5（報酬構造フィルタ）で行う。

#### フェーズによる通知カテゴリの使い分け

**実績（完了案件・レビュー）がまだ少ない間は、Tier A純度より母数を優先する。** 発注者は実績ゼロの応募者を選びにくく、専門性の高いTier A案件ほど通過率が下がる構造があるため、まず完了実績を作ってから純度を上げる方が結果的に早い。

⚠️ **緩めるのは「拾うカテゴリの範囲」だけ。** STEP 1（即時除外）の受注基準は実績の有無にかかわらず一切緩めない。AI利用禁止・時給1,000円未満などは、実績ゼロでも受けない。

**フェーズ1（`kpi-log.md` の完了案件 5件未満）**: 上記のTier A確定カテゴリに加えて以下もONにする。

| 追加カテゴリ | 理由 | 注意 |
|---|---|---|
| データ収集・入力・リスト作成 | 大半（実測9割）はタスク形式でTier Cだが、通知1通あたりの選別コストはほぼゼロなので母数を広げて損はない | タスク形式（1件◯円）は通知を見た時点で即除外。開いた案件には毎回STEP 2.5を適用する |
| 記事制作AI自動化 | 「記事を書くAI」ではなく「記事作成を自動化するツール開発」案件が混在する | 募集要項全文で用途を判別。ライティング単体なら除外 |

**フェーズ2（完了案件 5件以上）**: 上記2カテゴリをOFFに戻し、開発・自動化系のみに絞る。母数より単価と実効時給を優先する運用に切り替える。

### クラウドワークス
- [ ] 公式スマホアプリを入れ、**検索条件保存＋新着案件プッシュ通知**を有効化
  - ⚠️ 配信は**1日1回・昼12時頃**。リアルタイムではないので、通知だけに頼ると出遅れる
- [ ] 検索条件は**最大3つまで**しか保存できない。広めの語を束ねて配分する

  | 枠 | 割り当て |
  |---|---|
  | 1 | 自動化系（GAS・VBA・スプレッドシート） |
  | 2 | データ処理系（データ整形・CSV変換・スクレイピング） |
  | 3 | 開発系（Android・Kotlin・API連携） |

  枠に入らない語は手動検索で補う。

#### ✅ 実測で確認済みの経路（クラウドワークス／2026-09-01時点）
- **「本日の◯◯様向けおススメ案件」メール**（`info@sf.crowdworks.jp` から日次配信）が着信しており、**案件ソースとして既に機能している**。事務局ピックアップ案件が3件前後、予算と応募期限つきで載る
- ただし掲載されるのは**タイトル・予算・応募期限のみ**。Tier判定には募集要項の全文が必要なので、気になった案件はリンク先から本文をコピーして渡す
- **スカウト（「◯◯について相談がありました」メール）も着信するが、質は低い。** 実例: プロフィールと無関係な動画編集案件（1本4,000円＝実効時給1,000円台）が定型文で届いた。`job-screening.md` の即時除外に該当。**スカウトは経路として期待しない**

## 1日10分の巡回ルーティン

```
[ユーザー] 通知を確認                              2分
         → 保存した検索条件を新着順で巡回          5分
         → 気になった案件の募集要項をコピペ        1分/件
[Claude]   Tier判定 → 見積もり → 提案文の作成       —
[ユーザー] 内容を確認して送信                      3分/件
```

**巡回は毎日。提案はその場で送る。** 溜めた時点で速度の優位を失う。

## Claude に渡すときの定型フォーマット

毎回説明し直さずに済ませるためのテンプレート。そのままコピーして使う。

```
案件判定お願いします。

【募集要項】
（ここに全文を貼る）

【募集掲載日】
【現在の応募数】（表示されていれば）
【クライアントの評価】（表示されていれば）
```

### Claude の返答形式（固定）
1. Tier判定とスコア内訳（5項目のどれが何点か）
2. 即時除外に該当するか
3. 見積時間と提示額（`pricing.md` の逆算表による）
4. 提案文（`proposal-templates.md` の型）
5. 発注者に確認すべき点

⚠️ **Tier C 判定なら提案文は書かない。** 理由だけを返す。書いてしまうと「せっかく書いたから出そう」という誘惑が生まれ、フィルタが形骸化する。

## 週5件を確保できないときの対処

**この順序で発動する。飛ばさない。**

1. **検索語を増やす** — キーワード表の未使用語を試す
2. **プラットフォームを増やす** — クラウドワークスも巡回対象に入れる
3. **Tier B まで対象を広げる** — 欠けている項目を質問で埋められる案件に限る
4. **それでも足りなければ、提案せずに再利用資産の整備に時間を回す**

⚠️ **4が重要。Tier C には降りない。** 案件数が足りないことを理由に低単価案件を受けると、実効時給が崩壊したうえに評価毀損リスクだけが残る。空いた時間はテンプレート化・ポートフォリオ整備に使う方が、翌月以降の受注率に効く。

### 応募が集中している案件の扱い
募集から日数が経ち応募が多数集まっている案件は、優先度を下げる。同じ手間をかけるなら新着に使う。

本ファイルのキーワード表は `job-screening.md` の Tier A 定義からの**逆算であり、実際の検索結果では未検証**。運用開始後に直す。

- [ ] 各検索語で1週間に何件の Tier A 案件が出現するか数える
- [ ] ヒット0件が続く語は削る
- [ ] 想定外に良い案件が取れた語を追加する
- [ ] 受注できた案件がどの経路（通知／保存検索／スカウト）から来たかを `kpi-log.md` に記録し、経路ごとの効率を見る

**受注できた案件の「募集からの経過日数」が短い傾向が確認できたら、巡回頻度を上げる。** 速度が効くという仮説を、自分の実データで検証する。

## 実測: 初回スクリーニング（2026-09-01〜02）

`job-pipeline` ラベル全14スレッド・**実案件31件**にフィルタを適用した結果。

| 供給元 | 件数 | Tier B以上 | Tier C |
|---|---:|---:|---:|
| クラウドワークス おすすめ案件 | 3 | 1 | 2 |
| クラウドワークス スカウト | 1 | 0 | 1 |
| ランサーズ 開発系 | 3 | 1 | 2 |
| ランサーズ データ収集・タスク | 10 | 0 | 10 |
| ランサーズ ライティング系 | 14 | 0 | 14 |
| **合計** | **31** | **2** | **29** |

### 🔴 31件判定して Tier A はゼロ、Tier B が2件のみ

**さらにその2件は募集要項の全文確認後、いずれも見送り／辞退となった。**

| 案件 | 素点判定 | 全文確認後 |
|---|---|---|
| WordPress制作パートナー | Tier B | **見送り**（応募140人/募集2人＝競争率1.4%、掲載4日経過、応募資格にWordPress実務経験が必須、単価不成立） |
| 人件費異常検出AIエージェント | Tier B | **辞退**（賃金台帳＝区分3の機微情報、介護報酬のドメイン知識必須、必要稼働21.4h/週で枠超過） |
| 業務自動化・DX（Telegram/GAS） | — | **Tier B・提案推奨**（33件目。スコープ限定が条件） |

**教訓: 募集要項を取得する前の Tier 判定は暫定値。** メールに載るのはタイトル・金額・締切のみで、実際に判定を左右した以下はすべて全文にしかない。

- 応募数 / 募集人数（＝通過率）
- 掲載からの経過日数
- 応募フォームの必須項目（＝実質の応募資格）
- クライアントの本人確認状況
- 扱うデータの機微性

**供給不足ではなく、見ている場所が違う。** 上記「通知カテゴリの偏り」を数値で裏付ける結果であり、通知設定の絞り込みが最優先課題であることが確定した。

**判定に迷いは出ず、フィルタ自体は機能した。** ただし当初カテゴリ名で「データ入力」を一括除外しようとしたのは誤りで、実際の除外理由は報酬構造（タスク形式・予算上限5,000円・他社アカウント操作）にあった → `job-screening.md` STEP 2.5 を新設。

判定の詳細と見送り理由はNotionの「見送りログ（Tier C）」に記録している。
