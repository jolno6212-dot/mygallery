# 受注〜納品の標準作業手順

**設計思想: AIが担う工程と、人間が責任を負う工程を明確に分離する。**

AIは実装を高速化するが、「正しいと保証する」ことはできない。保証するのは事業者本人であり、そこが報酬の根拠になる。この手順書はその境界を工程として固定するためのもの。

---

## 秘密情報の取扱区分（着手前に必ず判定）

**AIに投入してよい情報の線引き。ここを誤ると契約違反・法令違反になる。**

| 区分 | 内容 | AIへの投入 |
|---|---|---|
| **区分1: 公開情報** | 公開ドキュメント、一般的な技術情報、OSSコード | ✅ 制限なし |
| **区分2: 業務情報** | 仕様書、非公開のビジネスロジック、社内フロー | ⚠️ **NDAと契約条項を確認**。生成AI利用禁止条項がなければ可 |
| **区分3: 機微情報** | 個人情報、認証情報、顧客リスト、決済情報 | ❌ **投入禁止** |

### 区分3への対処
- **匿名化・ダミー化して扱う。** 構造だけを再現したサンプルデータで開発し、実データはクライアント環境でのみ実行してもらう
- 匿名化できない場合は **案件自体を辞退する**（`job-screening.md` STEP 1 の即時除外項目）
- 認証情報（APIキー、パスワード）は**絶対にAIへの入力にもコードにも含めない**。環境変数・設定ファイル経由にし、`.gitignore` を必ず確認する

### NDA締結案件の追加確認
- [ ] NDAに「第三者への開示禁止」条項がある場合、外部AIサービスの利用が「開示」に該当しないかを確認する
- [ ] 「生成AI利用禁止」条項がある場合 → **受けない**
- [ ] 判断がつかない場合はクライアントに直接確認する。確認せずに進めない

## Phase 1: 提案（目標 30分以内）

1. **`job-screening.md` で判定** — Tier A/B のみ進む
2. **`pricing.md` で見積もる** — 工程別に時間を出し、1.5倍のバッファを掛け、逆算表で契約額を決める
3. **秘密情報区分を判定** — 区分3が避けられないなら辞退
4. **`ai-disclosure-policy.md` で申告要否を判定**
5. **`proposal-templates.md` から提案文を作成**
6. **`kpi-log.md` に提案を記録**

⚠️ 30分を超えたら、その案件は要件が複雑すぎる。Tier判定を見直す。

---

## Phase 2: 受注直後（着手前に必ず実施）

**ここを飛ばすと後工程が全て壊れる。最重要フェーズ。**

### 要件の確定
着手前に、以下を**テキストで**クライアントと合意する。口頭・ニュアンスでの合意は残さない。

- [ ] 成果物の具体的な形式（ファイル形式、納品方法、動作環境）
- [ ] **完了条件**（何ができれば「完成」なのか。これが曖昧だと無限に修正が続く）
- [ ] 動作環境・前提条件（OSバージョン、Excelバージョン、権限、既存システムとの連携有無）
- [ ] テストに使えるサンプルデータの有無
- [ ] 修正対応の範囲と回数（`pricing.md` の追加費用条件を提示）
- [ ] 納期

### 確認テンプレート
```
ご依頼ありがとうございます。着手にあたり、認識の齟齬を防ぐため
以下を確認させてください。

【成果物】
・◯◯（形式：△△）

【完了条件】
・◯◯が××できる状態

【動作環境】
・◯◯

【納期】
・YYYY年MM月DD日

【修正対応】
・上記完了条件の範囲内での修正は◯回まで無償で対応いたします。
　仕様の追加・変更が生じる場合は別途お見積もりのご相談をさせてください。

相違がございましたらご指摘ください。問題なければ着手いたします。
```

⚠️ **返答を得てから着手する。** 「たぶんこうだろう」で始めた作業は、高確率で作り直しになる。

## Phase 3: 実装（AI主導 / 時間圧縮の中心）

1. 確定した要件を仕様としてClaude Codeに渡す
2. 実装させる
3. **区分3の情報は絶対に投入しない**（ダミーデータで開発）
4. 実装中に仕様の曖昧さが判明したら、**推測で埋めずクライアントに確認する**

### 再利用資産の蓄積
同一タイプの案件を2件以上こなしたら、共通部分をテンプレート化して手元に残す。**これが実効時給を逓増させる唯一の仕組み**であり、時間の余剰を投下すべき先。

---

## Phase 4: 検証（人間が責任を負う工程 / ここは絶対に削らない）

**AI出力をそのまま納品しない。** 品質クレームの最大の原因であり、この工程こそが付加価値の実体。

### 全案件共通
- [ ] **実際に実行した**（「動くはず」ではなく、動かした）
- [ ] 要件の完了条件を1つずつ突き合わせた
- [ ] 正常系が期待どおり動く
- [ ] 異常系（空データ、想定外の形式、大量データ）で落ちない
- [ ] 認証情報・APIキー・個人情報がコードや成果物に混入していない
- [ ] クライアントの動作環境で動く（バージョン差異を確認した）

### コード・ツール案件
- [ ] クライアント環境と同等の条件で動作確認した
- [ ] エラーメッセージが利用者に理解できる内容になっている
- [ ] 使い方の説明（README / 手順書）を添えた

### データ処理案件
- [ ] 出力件数が入力件数と整合する（欠落・重複がない）
- [ ] サンプルを抽出して元データと目視で突合した
- [ ] 文字化け・型崩れ（日付、桁区切り、先頭ゼロ）がない

### 文章・調査案件
- [ ] 事実・数値の裏取りを一次情報で行った
- [ ] 存在しない情報源を引用していないか確認した（**生成AIで最も起きやすい失敗**）
- [ ] 剽窃チェックを行った

⚠️ **1つでもチェックが埋まらない状態で納品しない。**

---

## Phase 5: 納品

1. 成果物 + 使い方の説明を添えて納品
2. **納品メッセージで継続契約を提案する**（唯一の営業機会 → `proposal-templates.md`）
3. 検収・評価を待つ
4. **`kpi-log.md` に実績を記録**（見積時間 vs 実働時間、実効時給、Tier判定の妥当性）

---

## Phase 6: 振り返り（1件ごと・5分）

以下に該当したら、対応するドキュメントを**その場で改訂する**。後回しにすると同じ失敗を繰り返す。

| 起きたこと | 改訂先 |
|---|---|
| 見積と実働が1.5倍以上乖離した | `pricing.md` のバッファ係数、`job-screening.md` の判定項目 |
| 修正が3往復を超えた | `delivery-workflow.md` Phase 2 の確認項目 |
| 実効時給が2,000円/hを下回った | `job-screening.md` の Tier 分類 |
| 規約・AI利用で問題が起きかけた | `ai-disclosure-policy.md` |
| 提案が全く通らなかった | `proposal-templates.md` |
