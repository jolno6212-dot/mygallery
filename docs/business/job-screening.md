# 受注判定チェックリスト

この事業の中核。**領域では選ばない。「Claude Codeで完結する構造か」で選ぶ。**

案件ページを開いてから判定完了までの目標時間は **3分**。3分で判定できない案件は、それ自体が「仕様が曖昧」というシグナルなので Tier C 扱いにする。

---

## STEP 0: 判定に足る情報が揃っているか

**揃っていなければ判定しない。** メール通知に載るのはタイトル・金額・方式・締切だけで、実際に判定を左右する情報はすべて案件ページの全文にしかない。

- [ ] **募集要項の全文**を取得した（作業内容・応募条件・納品物・応募方法）
- [ ] **応募数と募集人数**（→ 通過率。STEP 4で使う）
- [ ] **掲載日**（→ 経過日数。STEP 4で使う）
- [ ] **クライアント情報**（本人確認・評価・募集実績・契約数）

⚠️ **タイトルと金額だけでの判定は暫定値。** 実測: 全文確認により3件すべて判定が変わった（Tier B → 見送り2件／新規Tier B 1件）。暫定判定で提案文を書き始めない。

## STEP 1: 即時除外フィルタ（1つでも該当したら即終了）

以下は完結度スコアを計算するまでもなく除外する。

- [ ] 募集要項に「AI利用禁止」「AI生成物不可」「ChatGPT等の使用禁止」の記載がある
- [ ] 稼働時間の拘束がある（「平日9-18時対応必須」「常駐」「稼働報告ツールの常時起動」）
- [ ] 音声通話・ビデオ面談が必須（初回商談だけなら可。恒常的な会議参加が必須なら除外）
- [ ] 報酬が時給1,000円以下、または文字単価0.5円以下
- [ ] クライアントの与信に問題がある（→ 下記「クライアント与信の見方」で判定）
- [ ] 「テスト案件は無報酬」と明記されている
- [ ] 個人情報（氏名・住所・電話番号・マイナンバー等）を含む生データを扱う
- [ ] 資格・免許が必要（士業、医療、有資格者限定）
- [ ] **応募フォームの必須項目に、正直に書けないものがある**（例:「◯◯の実務経験：制作年数・担当範囲・実績」を求められるが実績がない）

**除外は損失ではない。** 既存の評価アカウントを守ることが、この事業の最大の防御。

### クライアント与信の見方

> ⚠️ **総合評価と完了率だけを見ない。** 評価は「契約に至ったごく一部の母集団」からしか付かない。
> 実測例: 総合評価4.8・プロジェクト完了率100%でありながら、**66件募集して契約11件**、公開評価の複数が「テスト案件」に言及するクライアントが存在した。

| 確認項目 | 危険信号 |
|---|---|
| **募集実績と契約数の比率** | 募集数に対し契約数が極端に少ない（目安: **3割未満**）。大量に応募を集めるが契約しない構造 |
| **評価コメントの「テスト案件」** | 複数の評価が「テスト案件」に言及。継続を謳いながら小規模案件だけで終わる可能性 |
| **募集タイトルと発注実態の乖離** | 「継続」「パートナー募集」を掲げるが、記録に残る発注は低単価の単発 |
| **プロフィールと募集要項の矛盾** | 「未経験歓迎」を掲げつつ募集要項では経験必須、など |
| **本人確認 × 活動期間** | 長期間・多数の募集を経てもなお本人確認未提出 |
| 従来項目 | 評価が著しく低い／過去の募集で未払い報告がある |

**該当が複数重なるほど危険度が上がる。** 単独では即除外にしないが、2つ以上重なるなら見送る。

⚠️ ただし固定報酬制なら**仮払い（エスクロー）による支払い保護**が効く。与信の懸念は「未払い」より「**時間を投じても契約に至らない**」「**継続の約束が果たされない**」リスクとして評価する。

## STEP 2: Claude Code完結度スコア（5点満点）

各項目、明確に「はい」と言えるときだけ1点。迷ったら0点。

### ① 仕様が文章で完全に記述可能か
募集要項＋テキストの質疑応答だけで、作るべきものが一意に決まるか。
- ✅ 「このスプレッドシートのA列をキーにB列を集計し、日次でメール送信」
- ❌ 「いい感じにデザインしてほしい」「弊社の雰囲気に合わせて」

### ② 成果物がテキスト / コード / 構造化データか
- ✅ ソースコード、スクリプト、CSV/JSON、設定ファイル、技術文書
- ❌ 動画編集、手描きイラスト、電話代行、現地撮影

### ③ 正しさを自分で検証できるか
**最重要項目。** 納品前に自分で「合っている」と確認できるか。
- ✅ 実行して動く／テストが通る／出力データを元データと突合できる
- ❌ 「バズるかどうか」「読者に刺さるか」など、他人の主観が合否を決める

### ④ クライアント固有の非公開ドメイン知識が不要か
- ✅ 一般的な技術・公開情報の範囲で完結する
- ❌ 社内の業務フロー・既存の巨大なレガシー資産・暗黙のルールを前提とする

### ⑤ AI利用が規約・募集要項で許容されているか
STEP 1 で明示的な禁止は除外済み。ここでは **「記載がない」場合の判断**：
- ✅ 成果物がコード／自動化スクリプト → 記載がなければ問題になりにくい（道具の使用と解釈される）
- ⚠️ 成果物が文章・記事 → 記載がなくても 0点。`ai-disclosure-policy.md` の申告手順を踏むこと

## STEP 2.5: 報酬構造フィルタ（速さが報酬に転換されるか）

**完結度スコアが高くても、報酬構造が悪ければ実効時給は上がらない。** AIで10倍速くなっても、その速さが報酬に変わらなければ意味がない。

発注者は「手作業なら何時間かかるか」で値付けする。**そのギャップが利益の源泉**なので、ギャップを回収できる構造かを必ず見る。

| 報酬形態 | 納品形式 | 判定 |
|---|---|---|
| **固定報酬** | **ファイル納品**（CSV/スプレッドシート/コード） | ✅ **最良。作業量が多いほど有利になる** |
| 固定報酬 | プラットフォーム画面での逐次入力 | ❌ 自動化できない |
| タスク（1件◯円） | 画面入力 | ❌ 単価が極小。承認率の管理コストも乗る |
| 時給制・稼働時間連動 | 何であれ | ❌ **速くしても報酬が増えない。むしろ減る** |

### 判定の手順
- [ ] **固定報酬か**（時給制・稼働時間連動なら受けない → `pricing.md` の「常に固定報酬で見積もる」原則）
- [ ] **成果物をファイルで納品できるか**（他社サービスの画面に手入力する形式は自動化できない）
- [ ] **他社プラットフォームのアカウント操作を含まないか**（自動化がそのサービスの規約に触れる。例: EC出品代行）
- [ ] **予算の上限額が目標に見合うか** — 上限5,000円の案件は、どれだけ速く終わらせても5,000円が天井。`pricing.md` の逆算表で下限を割らないか確認する
- [ ] **作業量が多いか** — 少量だとAIの速度優位が出ず、要件確認のオーバーヘッドが相対的に重くなる

⚠️ **「データ入力・データ収集」を案件名やカテゴリ名だけで切らないこと。**
固定報酬 × ファイル納品 × 大量データの組み合わせなら、これは **Tier A の中でも最も有利な案件タイプ**になる。実際 Tier A の「データ整形・変換・クレンジング」がそれ。
逆にタスク形式・時給制・画面入力なら、名前が何であれ除外。**判断するのは名前ではなく構造。**

## STEP 3: Tier 判定

| スコア | Tier | 対応 |
|---|---|---|
| 5点 | **A** | 最優先。即提案する |
| 4点 | **B** | 欠けている項目を質問で埋められるなら提案。埋まらなければ辞退 |
| 3点以下 | **C** | **受けない** |

### Tier A の典型例（＝探しに行くべき案件）

| 案件タイプ | 相場 | 想定実働 | 備考 |
|---|---|---|---|
| GAS / スプレッドシート自動化 | 30,000〜80,000円 | 8〜15h | **最有力**。仕様が明確で検証も容易 |
| Excel VBA / マクロ作成 | 20,000〜60,000円 | 6〜12h | 需要が安定 |
| スクレイピング / データ収集ツール | 30,000〜80,000円 | 10〜20h | 対象サイトの規約確認は必須 |
| データ整形・変換・クレンジング | 15,000〜50,000円 | 5〜12h | **固定報酬×ファイル納品なら最有利**。量が多いほど有利。継続契約化しやすい |
| 小規模Webツール / 業務ツール | 30,000〜100,000円 | 12〜25h | |
| Androidアプリのバグ修正・小改修 | 20,000〜80,000円 | 8〜20h | **`mygallery` を実績提示できる領域** |
| API連携 / 定型バッチ処理 | 30,000〜80,000円 | 10〜20h | 継続化しやすい |

### Tier B（条件を確認してから）
LP制作、既存コードのリファクタ／テスト追加、技術文書・仕様書作成、AI利用が明示的にOKな記事作成。

#### 例外: 素点が3点でも Tier B として扱う場合

**①スコープ未定義・④固有システム依存で落ちていても、「こちらからスコープを定義すれば埋まる」案件は Tier B とする。**

Tier B の定義は「欠けている項目を**質問で埋められるなら**提案」だが、質問ではなく**提案で埋める**ケースがある。

| 症状 | 埋め方 |
|---|---|
| 「まずは一例です」「一緒に確認しながら」でスコープが未定義（①） | **第1弾のスコープを自分から定義して提案する** |
| クライアント固有の非公開システムへの依存（④） | **第1弾からその連携を外す**。公開APIだけで完結する範囲を切り出す |
| 列挙された要件量に対して予算が小さい | スコープを予算に合わせる。提示額は第1弾の予算と解釈する |

**成立条件**（すべて満たすこと）:
- 切り出した第1弾スコープが、`pricing.md` の逆算表で許容時間内に収まる
- 第1弾が公開APIや一般的な技術だけで完結し、④の依存を回避できている
- 機微情報（区分3）を扱う要素を第1弾から外せている
- **スコープを絞る理由を「進め方の提案」として書ける**（値切りと読まれる書き方にしない）

⚠️ これは判定を甘くする抜け道ではない。**自分でスコープを設計できない案件には使えない。** 何を第1弾にするか具体的に書けないなら、それは Tier C。

### Tier C（受けない）
AI利用禁止のライティング、深い業務ドメイン知識が前提の開発、常駐・時間拘束、タスク形式の作業、時給制の案件、他社サービスの画面への逐次入力、デザインセンスが合否を決める案件。

## STEP 4: 提案前の最終確認

Tier A/B と判定した後、提案文を書く前に確認する。

- [ ] **納期にバッファを1.5倍取れるか**（見積10h → 15h分の余裕がスケジュール上あるか）
- [ ] 現在の進行中案件と合わせて、週の稼働枠（10〜20時間）を超えないか
- [ ] 秘密情報の取扱区分を判定したか → `delivery-workflow.md`
- [ ] AI利用の申告が必要な区分か → `ai-disclosure-policy.md`
- [ ] 想定実効時給が 2,000円/h を超えるか → `pricing.md` の計算式で確認

### 競争環境と期間の確認（実測から追加）

| 項目 | 目安 | 根拠 |
|---|---|---|
| **応募数** | 50件未満なら通常。**50〜100件**は「具体的な構成案を求める案件」のみ。**100件超は原則見送り** | WordPress案件は応募140人・募集2人（通過率1.4%）。競合に専門家が並び、勝ち目がなかった |
| **通過率**（応募数÷募集人数） | **5%未満は見送り** | 同上 |
| **掲載からの経過日数** | 3日以内が理想。**7日超は優先度を下げる** | 募集直後は発注者がまだ本気で読んでいる。日数が経つと候補が固まる |
| **拘束期間** | 週10〜20hの枠で **6週を超える単一案件は受けない** | 人件費AI案件は6〜13週。その間ほかのTier A案件を取れなくなる |

⚠️ **上記の閾値は実測3件からの暫定値。** `kpi-log.md` に受注/落選の応募数と経過日数が10件たまったら、自分の実データで較正すること。

**1つでも満たさなければ提案しない。**

## 判定ログ

判定した案件は結果を `kpi-log.md` に記録する。受注できなかった案件も記録すること。受注率と、どのTierが実際に取れているかが、フィルタの精度を測る唯一のデータになる。

## フィルタの改訂ルール

以下が起きたら、このチェックリストに項目を追加する（＝同じ失敗を二度しないための仕組み）。

- 見積時間と実働時間が **1.5倍以上** 乖離した → 何を見落としたかを①〜④のどこかに項目化
- 低評価・修正の往復が3回を超えた → その原因を STEP 1 か STEP 4 に追加
- 実効時給が 2,000円/h を下回った → Tier判定が甘い。該当案件タイプを Tier B/C に降格
