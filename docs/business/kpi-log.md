# 案件ログ・KPI管理

**計画の正しさは「読んで納得できるか」では検証されない。実測値だけが判断材料になる。**

このファイルは記録簿であり、判断の根拠。ここが空のまま単価や戦略を変えてはいけない。

---

## 追跡する指標

| 指標 | 目標値 | 意味 |
|---|---|---|
| 週あたり提案数 | **5件以上** | 最大のボトルネック。ここが落ちると全てが止まる |
| 受注率 | 10〜20% | 10%未満 → 提案文かターゲット選定の問題 |
| 見積乖離率（実働÷見積） | 1.5倍以内 | 超えたら見積係数を較正 |
| 実効時給 | **3,000円/h以上** | 2,000円未満は `job-screening.md` の失敗 |
| 月商 | 50,000〜100,000円 | |
| 評価 | 維持 | **低評価1件の損失は報酬額を上回る** |

## 提案ログ

> 🔗 **正はNotionの「案件パイプライン」DB。** 案件ごとの詳細（判定内訳・見積・提案文・注意事項）はNotion側で管理し、**二重入力しない**。
> 本ファイルは判断ルール・月次サマリ・四半期レビューを担う。下表はNotionが使えない場合のフォールバック。

提案した全案件を記録する。**落ちた案件こそ記録する** — 受注率とフィルタ精度は、落選データがないと計算できない。

| 日付 | 案件名 | PF | 経路 | 経過日数 | Tier | スコア | 提示額 | 見積h | 結果 | 備考 |
|---|---|---|---|---|---|---|---|---|---|---|
| | | | 通知/検索/スカウト | 日 | | /5 | 円 | h | 提案中/受注/落選 | |

<!-- 記入例
| 2026-09-05 | スプレッドシート日次集計の自動化 | ランサーズ | 通知 | 0 | A | 5/5 | 45,000 | 12 | 受注 | 競合5件 |
| 2026-09-06 | 記事作成（AI利用要申告） | ランサーズ | 検索 | 4 | B | 4/5 | 20,000 | 8 | 落選 | 申告後に返信なし |

**PF** = プラットフォーム（ランサーズ / クラウドワークス / ココナラ）
**経路** = どこから見つけたか（新着通知 / 保存検索の巡回 / スカウト）→ 経路ごとの効率を測り、`job-sourcing.md` を較正する
**経過日数** = 募集掲載日から提案日までの日数。**速度が受注率に効くという仮説を自分の実データで検証するための列**

## 判断ルール（数値が出たら機械的に実行する）

感覚で判断しない。以下は該当したら必ず実行する。

| 観測値 | 実行すること |
|---|---|
| 週の提案数 < 5件 | **最優先で提案数を戻す**。他の改善より先 |
| 提案20件で受注0 | `proposal-templates.md` の冒頭3行と価格帯を見直す |
| 受注率 > 30% | **単価が安すぎる**。次の案件から15〜20%上げる |
| 見積乖離 > 1.5倍が3件連続 | `pricing.md` のバッファ係数を実測値に置き換える |
| 実効時給 < 2,000円/h | その案件タイプを `job-screening.md` で Tier 降格 |
| 実効時給 > 4,000円/h が3件 | その案件タイプに集中。テンプレート資産化を優先 |
| 修正が3往復超 | `delivery-workflow.md` Phase 2 の確認項目を追加 |
| 受注案件の経過日数が落選案件より明確に短い | 速度が効いている。**巡回頻度を上げる**（毎日→朝夕2回） |
| 特定の経路からの受注が0 | その経路の設定を見直す。改善しなければ巡回対象から外して時間を他に回す |
| 低評価を受けた | **新規受注を止めて原因分析**。アカウントの保護を最優先 |
