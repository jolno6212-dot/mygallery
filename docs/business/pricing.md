# 価格設計と実効時給

**原則: 価格は「かかった時間」ではなく「引き受けた責任」で決める。**

AIによって実行時間は圧縮されるが、成果物の正しさを保証する責任は圧縮されない。時間で値付けすると、AIで速くなるほど自分の報酬が下がるという逆インセンティブが働く。**この事業では常に固定報酬（プロジェクト単位）で見積もる。**

---

## 0. 初回受注体験モード（期間限定の例外運用）

**目的: 受注→納品→着金という流れを一度体験すること。** 実績ゼロの段階では単価最適化より「まず1件終わらせる」方が学びが大きい。**ただし `job-screening.md` STEP 1（即時除外基準）は例外なく維持する。** AI利用禁止・拘束系・未払いテスト案件・生PII・与信不良クライアントは、初回受注体験モードでも受けない。緩めるのは単価と規模の判断だけ。

### 緩和する項目

| 項目 | 通常運用 | 初回体験モード |
|---|---|---|
| 目標実効時給の下限 | 3,000円/h | **1,500円/h**（Step 3の逆算式にこの値を使う） |
| Tier閾値 | A/Bのみ提案 | スコア3〜4のBも積極的に拾う（`job-screening.md` STEP 3のTier B例外条項を緩めに運用） |
| 案件規模 | 問わない | **小規模・短納期を優先**（数時間〜1日で完結する案件）。学習サイクルを速く回すことが目的 |
| 価格提示 | 見積もりレンジの中央値 | レンジの**下限寄り**で提示し、価格でも勝ちやすくする |

⚠️ **1,500円/hは最低賃金を上回っていることが前提。** 都道府県の最低賃金を下回る単価は、体験目的であっても提案しない。STEP 1の「時給1,000円未満は即時除外」は、あくまで最終防衛ラインであり目標値ではない。

### 緩めてはいけない項目

**初回受注体験モードで緩めるのは「単価」「Tierスコアの閾値」「案件規模の好み」の3つだけ。** `job-screening.md` STEP 2 の完結度スコアのうち、以下は実績の有無にかかわらず不合格のまま扱う。

- **②成果物がテキスト/コード/構造化データであること。** クライアントの実環境（管理者ポータル・実機）に入って手を動かす作業（IT インフラの実機設定、多数の端末個別対応など）はここで不合格
- **③成果の正しさが自己検証可能であること。** Claude Codeのサンドボックスで検証できず、クライアント環境で初めて正否が決まる仕事は不合格
- **④クライアント固有の非開示ドメイン知識が不要であること。** 「情シス代行」のような、専門資格レベルの実務経験を前提とする仕事は不合格

**単価が良く応募も少ない（＝当選しやすい）案件ほど、この3条件を緩めたい誘惑が強い。** しかし②③④で落ちる仕事は「安く受けたが遂行できない仕事」であり、初回体験どころか最初の低評価に直結する。実例: MS365・Intune移行案件（10〜20万円・応募1件）は単価も競争率も良好だったが、②③④すべてで不合格のため見送り（2026-09-06）。

### 終了条件

**初回受注が1件成立した時点で、次の案件から通常運用（目標実効時給3,000円・Tier A/B基準）に戻す。** `kpi-log.md` の完了案件ログに1件目が記録された時点がトリガー。このモードを恒常化しない。

## 2. 実効時給の計算式

```
実効時給 = 契約額 × (1 - 手数料率) ÷ 総投下時間

総投下時間 = 案件調査・提案作成 + 要件確認のやりとり
           + 実装（AI実行の待ち時間を含む）
           + 検証・テスト
           + 修正対応
           + 納品・請求事務
```

**「実装時間」だけで計算してはいけない。** この事業でAIが圧縮するのは主に実装時間だけであり、それ以外の工程は残る。実装だけを見て「時給1万円」と錯覚すると、単価を下げる判断につながる。

### 計算例：GAS自動化案件（ランサーズ）

| 項目 | 時間 |
|---|---:|
| 提案作成・要件確認 | 2.0h |
| 実装（Claude Code） | 4.0h |
| 検証・テスト | 3.0h |
| 修正対応（1往復） | 2.0h |
| 納品・事務 | 1.0h |
| **総投下時間** | **12.0h** |

```
手取り  = 50,000 × (1 - 0.165) = 41,750円
実効時給 = 41,750 ÷ 12.0      = 3,479円/h  ✅
```

### 判定基準

| 実効時給 | 判定 |
|---|---|
| 3,000円/h 以上 | ✅ 目標水準。この案件タイプを増やす |
| 2,000〜3,000円/h | ⚠️ 許容範囲。工程のどこが重いか記録する |
| 2,000円/h 未満 | ❌ **フィルタの失敗**。案件タイプを Tier 降格し、`job-screening.md` を改訂 |

## 3. 見積もりの手順

### Step 1: 総投下時間を見積もる
工程ごとに時間を出す。**実装以外の工程を必ず計上する。**

### Step 2: バッファを掛ける
```
提示用時間 = 見積時間 × 1.5
```
1.5倍は悲観ではなく**実測に基づく係数**。初期はこの値を使い、`kpi-log.md` の実測データが10件たまったら自分の実際の乖離率に置き換える。

### Step 3: 単価を逆算する
```
最低契約額 = 目標実効時給 3,000円 × 見積時間 ÷ (1 - 手数料率)
```

**目標実効時給3,000円・ランサーズの逆算表:**

| 見積時間 | 最低契約額 | 提示額（丸め） |
|---:|---:|---:|
| 5h | 17,964円 | **20,000円** |
| 8h | 28,743円 | **30,000円** |
| 12h | 43,114円 | **45,000円** |
| 15h | 53,892円 | **55,000円** |
| 20h | 71,856円 | **75,000円** |

**この額を下回る提示はしない。** 下回るくらいなら提案しない。

### Step 4: 納期を決める
```
提示納期 = 提示用時間 ÷ 週あたり投下可能時間 + 3日
```
週の稼働枠は10〜20時間。並行案件があればその分を引いて計算する。**最後の3日は必ず確保する**（検証と修正のバッファ。ここを削ると低評価に直結する）。

## 4. 追加費用を請求する条件

以下は当初見積もりに含めない。発生した時点で**追加見積もりとして提示する**（黙って飲み込まない）。

- 当初仕様になかった機能の追加
- 3往復を超える修正対応
- クライアント側の事情による仕様の作り直し
- 想定外の環境・レガシー資産への対応
- 納品後の保守・運用

提案文に必ずこの一文を入れる:
> 上記は提示いただいた要件に基づく見積もりです。仕様の追加・変更が発生する場合は、別途お見積もりのうえご相談させてください。

## 5. 継続契約の設計

**この事業の収益安定化の要。** 継続契約では提案・営業の工程がゼロになるため、同じ作業量でも実効時給が大きく上がる。

| 形態 | 月額目安 | 内容 |
|---|---|---|
| 定期データ処理 | 10,000〜30,000円 | 月次のデータ整形・レポート生成 |
| ツール保守 | 10,000〜20,000円 | 納品済みツールの不具合対応・軽微な改修 |
| 定期改修枠 | 20,000〜50,000円 | 月N時間までの改修対応 |

**単発案件の納品時が唯一の営業機会。** 納品と同時に「月次で運用を引き受けることも可能です」と提案する。これを `proposal-templates.md` の納品テンプレートに組み込んである。

---

## 6. 値上げの判断基準

以下の条件が揃ったときのみ、次の案件から単価を上げる（既存の継続契約は据え置き、または事前相談）。

- 同一タイプの案件を **3件以上** 完遂している
- その案件タイプのテンプレート／再利用資産ができている
- 直近の評価が維持されている
- 実測の実効時給データが `kpi-log.md` にある

**値上げ幅は 20% を上限とする。** それ以上は受注率が急落する。
